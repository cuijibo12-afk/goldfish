# 第四阶段：Embedding 混合检索、成本与遗留错误

2026-11-04。分支 `phase-d/embedding-performance`。已经实施和真实测试，保留 SQLite 记忆实体、独立 Provider、原话证据与 DSH `agent/pre-step` 自动注入；未增加 Agent 记忆工具。

**结论：保留原检索为默认。** 实际本地 Embedding 已接通，混合加精排显著降低 LLM 输入，但向量和无精排混合未稳定优于原方案，精排后的必要事实探针也未全面保持第三阶段水平。新方案可显式切换，不能宣称整体记忆质量达标。

## 审计、实现与版本

先阅读 [PHASE_B](PHASE_B.md)、[PHASE_C](PHASE_C.md)、正式任务书和现有源码，执行原80项Python、13项插件测试。主要发现：

1. 已有 Embedding 协议与向量表，但没有内容hash/版本校验、更新竞态保护和真实模型评测。语义排序先运行，查询向量后计算，因而不能减少 LLM 候选。
2. 单个无效画像会使整批有效事实及游标回滚。q14 的行为画像可能被词面候选截断或被模型以“不证明天生人格”为由丢弃。q13 同义概括与画像能同时占注入位置。
3. 图扩散收益未证明，继续默认0层；没有用向量接近程度认定同事件、因果或矛盾。

核心变更：

- `engine.py` 增量迁移到 schema 3。向量记录包含模型身份、显式revision、内容hash、概括版本和维度；网络返回后复查快照，拒绝将旧向量写到已修改概括。更新保留 `summary_revisions`，归档移出索引、保留原话。旧无hash向量须重建；模型/端点/revision/查询前缀变化会失效重建。
- SQLite 继续本地余弦扫描；缓存向量解码结果，外部连接的 `data_version` 及本连接写入使缓存失效。查询向量缓存最多128条、5分钟，模型身份参与key。没有引入分布式数据库或未经评测的ANN。
- 优先索引具体概括；画像单独辅助索引以保护交互期望/实际行为；主题和有效关系理由可选，默认不开。辅助索引同样检查内容hash与有效状态。启动持续排空，整理后增量更新，手工重建超过一批后继续后台处理。
- `retrieval.py` 并列融合向量、关键词、主题、时间，保护具体线索和多个指定时段；一般最多8条概括，条件变化问题最多再补2条文档邻居，另最多3条画像。邻居只是候选，不建立关系或因果。显式图扩散最多补一个空位，不挤掉直接候选。
- `semantic.py` 在有限候选上精排；简单精确查询可跳过排序，已有上下文则另做覆盖。对共享来源的同批记录按需审查重复，只有完整覆盖、逐字引用及数字/标识符检查通过才抑制。向量分数不能授权删除或完整覆盖。
- `consolidate.py` 逐项沿用严格证据/角色/日期校验，无效项及依赖它的边写入 `consolidation_rejections`。有效项、拒绝记录与游标一起事务提交；磁盘或提交失败仍整体回滚。破坏顶层结构、超过输出上限仍整批拒绝，没有放宽来源检查。

新集冻结提交 `4c80c84`；排序/提取实现冻结 `2450ba6`，随后才揭示新集输出。之后仅做：旧q14暴露的注入理由安全修复 `f584c31`、手工重建的后台续批修复、评测来源目录纠错与报告；没有根据新集修改候选、模型提示词或排序参数。
